# 네비게이션 앱 개발 가이드 (시행착오 · 문제점 · UE 이식)

> **대상**: 실제 UE5 앱에 네비게이션 기능을 구현할 사람.
> **목적**: 서버 담당이 만든 **임시 검증용 안드로이드 앱(`nav-test-app`, Kotlin)** 으로 실공간 워킹
> 테스트를 하며 겪은 **시행착오·문제·해결·미해결**을 남겨, 실제 앱에서 같은 함정을 반복하지 않게 한다.
> 서버 계약은 `docs/nav-server-integration-guide.md` 참조.

---

## 0. 요약 — 검증된 것 / 남은 것

**검증됨 (실기기 Galaxy S21):**
- ✅ **세계 고정** — QR 하나로 서버 맵을 실공간에 고정, 노드/경로가 세계에 붙어 안 흔들림.
- ✅ **정밀 위치 추적** — 걷는 동안 내 위치가 맵 좌표로 실시간·정확히 추적됨.
- ✅ **서버 계약 성립** — route/reroute가 실공간에서 올바른 경로·안내를 줌.

**미해결 (실제 앱에서 반드시 다뤄야 함):**
- ❗ **턴바이턴 진행 없음** — 안내 문구가 정적(전체 경로를 한 번에 표시, 진행에 따라 안 넘어감).
- ❗ **경로 이탈 오판정** — 코너 과주행 + 폰-발 오프셋 + 디바운스 없음.

---

## 1. 핵심 교훈 (엔진 무관, 먼저 읽기)

1. **측위의 "방향"은 폰이 아니라 마커에서 얻어야 한다.** 카메라 yaw를 마커 heading으로 근사하면 폰 드는 대로 경로가 회전한다. → **마커의 실제 pose(위치+방향)** 를 써야 한다.
2. **측위는 한 번 확정(latch), 재측위는 의도적으로만.** 매 프레임 재측위하면 요동.
3. **좌표 변환의 축·부호·오프셋은 현장 1회 캘리브레이션이 필요.** (아래 문제3)
4. **경로 이탈 판정은 측위 정확도에 종속.** 측위가 틀어지면 이탈 오판정이 총 경로의 20~30% 지점에서 터진다. 이탈 로직보다 측위를 먼저 고쳐라.
5. **위치는 "폰"이지 "발"이 아니다.** 폰을 앞으로 내밀면 판정이 앞서 나간다. 도착 반경으로 흡수해야 한다.

## 2. 문제별 상세

### 문제1 — "정면"이 현실이 아니라 폰 기준 (치명적 → 해결)

- **증상**: QR 스캔 후 경로 정면이 폰 드는 방향대로 흔들림. 바닥 QR을 내려다볼 때 특히 심함.
- **원인**: 마커 heading을 **카메라 yaw**로 근사(ML Kit은 QR 내용만 디코딩, pose는 안 줌) + 매 프레임 재측위 + 바닥 QR 응시 시 카메라 yaw가 수직이라 불안정.
- **해결**: **ARCore Augmented Images(이미지 트래킹)** 로 교체. ARCore가 QR의 **6DoF pose를 세계 좌표로 직접** 준다.
- **원리(왜 QR 하나로 세계가 고정되나)**: ARCore(VIO)는 이미 안 흔들리는 세계 좌표계 + 중력("위")을 가진다. QR pose ↔ 서버 마커 맵pose 대응 한 쌍이면, 바닥 수평 가정 하에 **수직축 회전+평행이동**만 풀면 되고 스케일 1:1 → 점 하나+방향 하나로 맵 전체가 고정. 스캔 각도·방향 무관(QR 자체 방향이 기준).

### 문제2 — 턴바이턴 없음 + 이탈 오판정 (미해결)

- **증상**: (a) 노드 도착해도 다음 노드로 안내가 안 넘어감. (b) 코너를 220cm쯤 지나면 도착처럼 인식되며 동시에 150cm 이탈 알림.
- **원인**: (a) 진행 상태 머신 부재(경로 전체를 정적 렌더). (b) 이탈 판정이 전체 경로선 최단거리로만 계산 + 코너 과주행 + 폰-발 오프셋 + 디바운스/쿨다운/가드 없음.
- **해결 방향(권장)**:
  - **현재 목표 노드 인덱스** 상태 머신: 노드 반경(예 120cm) 진입 시 도착→다음 전환, 현재 step만 표시.
  - **진행 기반 이탈 판정**: 현재 구간까지 거리로 판정 + 노드 근처 억제 + N프레임 연속일 때만 + 쿨다운 + in-flight 가드.
  - 도착 반경 ~1.2~1.5m(폰-발 흡수), 이탈 임계 ~2~2.5m.

### 문제3 — 경로 90°/180° 회전 (해결: 캘리브레이션)

- **증상**: QR을 정면 보고 스캔했는데 화살표가 옆(90°)·정반대(180°)로.
- **원인**: 서버 heading(맵 +X 기준 CCW) ↔ ARCore yaw(`atan2(x,z)`) 규약 불일치 + `mapToLocal`의 (x,z,-y) 리맵. **UE5에선 좌표계가 서버와 같아 이 문제가 크게 줄어든다.**
- **해결**: 단일 보정각 상수(`HEADING_OFFSET_DEG`)로 현장 1회 정렬. 정면OK / 옆90°=±90 / 뒤=180 / 거울=축 y부호.

### 문제4 — 화살표 색이 변함 (경미, 오해 소지)

- **증상**: 바닥 화살표 색이 검정↔노랑↔초록.
- **원인**: 화살표는 초록 하나로 고정인데, **빛 영향을 받는(lit) 재질** + ARCore 주변광 추정 → 밝기/색조 변화. 의미 없음.
- **해결**: 안내 요소는 **unlit/emissive 재질**로 색 고정.

## 3. 서버/데이터·빌드 함정

- **시드 반영 3박자**: DB 노드/엣지 삭제 → 재시드 → **uvicorn 재시동(그래프 캐시 리셋)**. 노드 재삽입 시 **node_id 갱신**되니 앱도 재실행(destinations 재수신).
- **시더 멱등**: label로 매칭 → label 바꾸면 중복 삽입. 값 변경은 "삭제 후 재시드".
- **빌드 JDK**: 프로젝트 Kotlin 컴파일러가 최신 JDK(25) 파싱 실패 → **JDK 17**로 빌드(`JAVA_HOME=.../openjdk@17`).
- **디버그 미니맵**: 우측 상단 2D 미니맵(경로 폴리라인 + 실시간 파란 원=내 위치)을 붙이면 이탈·도착 문제를 눈으로 잡기 쉽다. 경로선(서버 정답)과 원(측정 위치)은 독립이라, 원이 선에서 벗어나는 양=측위 오차/과주행이 그대로 보인다.

## 4. 실제 앱(UE5 모바일 ARCore)으로의 이식

**타겟 확인**: 실제 앱 `TimeMachineAR`(UE 5.4)은 `feature/hybrid-ar-tracking` 브랜치에서 **GoogleARCore(Android) + AugmentedReality 모듈** 사용 = **모바일 ARCore**. (Quest/OculusXR는 꺼짐)

**UE 앱은 이미 우리가 검증한 구조를 갖고 있다** — `ARTrackingManager.cpp`:

| UE `ARTrackingManager` | Kotlin 검증본 | 역할 |
|---|---|---|
| `UARSessionConfig` 후보 이미지 라이브러리 | `AugmentedImageDatabase` | 마커 이미지 등록 |
| `GetAllGeometriesByClass(UARTrackedImage)` | `getUpdatedTrackables(AugmentedImage)` | 추적 이미지 조회 |
| `TrackedImage->GetLocalToWorldTransform()` | `augmentedImage.centerPose` | **마커 6DoF 월드 pose** |
| `PinComponent(...)` → `UARPin` + `bIsAnchored` | `AnchorNode` + 측위 latch | 앵커 고정·핸드오프 |

- **문제1을 UE는 이미 회피** — `GetLocalToWorldTransform()`이 마커 실제 pose를 줌(카메라 yaw 근사 아님).
- **좌표 변환이 더 쉬움** — 서버 좌표=UE5 Z-up cm라, `월드←맵 = 이미지월드transform × inverse(마커맵transform)` 한 줄. ARCore Y-up 리맵/90° 싸움 대부분 불필요.
- **마커 식별**: `TrackedImage->GetDetectedImage()->GetFriendlyName()`로 code 얻어 서버 마커와 매칭.

**현재 UE의 `ARTrackingManager`는 마커 pose에 공룡 오버레이를 스폰**할 뿐, 네비엔 안 쓴다. 네비를 얹으려면 그 pose를 **맵↔월드 변환 수립**에 재사용 → 서버 route → 웨이포인트를 월드로 → 경로 렌더 → 위치 추적/턴바이턴/이탈.

**여전히 적용되는 교훈**: 문제2(턴바이턴·이탈 하드닝) 필요, 문제3(앵커 기준 회전 1회 확인), 문제4(unlit 재질), 미니맵 디버깅.

## 5. 후속 과제 (우선순위)

1. UE 네비 통합 — `ARTrackingManager` 마커 pose → 맵↔월드 변환 → 서버 경로 렌더.
2. 턴바이턴 진행 상태 머신(문제2a).
3. 이탈 판정 하드닝: 디바운스/쿨다운/in-flight 가드 + 노드 근처 억제(문제2b).
4. 화살표 unlit 재질(문제4).
5. 중간 노드 QR로 드리프트 보정(정확도, 선택).
